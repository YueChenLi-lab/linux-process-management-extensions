# 三页创新讲稿与实测插图

原 PPT 保持原样。下面讲稿适合配合当前创新三页使用；若制作汇报实测版，请另存副本。每页约 45–70 秒，按正常中文讲述速度酌情停顿。

## 第 1 页：PCB 双队列不变量测试（约 60 秒）

原实验用按键观察进程阻塞和唤醒，但只看屏幕，很难发现尾指针没清空、一个节点重复入队这些问题。我们的扩展是把每个操作变成可复现事件，操作后立即检查不变量：每个活动 PCB 只能属于一条队列，链表必须无环，头尾指针一致，状态还要与队列对应。特别注意，运行节点就在 ready 队首，状态是 R，不能把 ready 全部断言为 w。本次运行了十个种子、五万次独立参考模型对照，还故意制造七类错误确认检测器能抓住。现场展示的 CSV 逐步给出操作、队列快照与 PASS，失败则报告第一个违规步骤。这里验证的是教学状态机，不是直接检测 Linux 内核队列。

现场命令（已编译后）：

```bash
./build/pcb_queues --demo
```

追问：为什么所有未完成进程不只从两条链表里遍历检查？

答：单看链表找不到已经丢失的节点。所以另保留 PCB 注册表，遍历后核对每个未完成记录必须出现一次，才能检测“不见了”的进程。

插图：`results/pcb/state_trace.png` 可替换左侧模型区，保留右侧四类检查。脚注把“待代码验证”改成“本次实测：17 步演示全部通过；50,000 次参考对照”。3,550,381 是断言数，不能写成独立测试案例数。

## 第 2 页：三算法统一工作负载（约 60 秒）

原实验分别跑三种算法，可以看懂规则，却不能据此比较效率，因为任务条件可能不同。现在三种算法读取同一份任务文件，A、B、C 都在零时刻到达，运行量分别为五、二、三。我们用理论时间线检验实现，再从程序实际输出画甘特图。本次 FCFS 平均等待为四，非抢占 SJF 为二点三三，RR 时间片二时为四点三三；但 RR 首次响应均值只有二，比另两种更快。这个对比说明等待时间和响应时间是不同目标。上下文切换分别为二、二、五，且没有给切换附加耗时。因此结论只针对这个零开销、单 CPU 的教学模型，不能说某算法永远最好，更不能把它当成真实 Linux 调度测试。

现场命令：

```bash
./build/scheduler examples/workload_baseline.csv rr 2 /tmp/rr-demo
cat /tmp/rr-demo.tasks.csv
```

追问：RR 时间片结束同时有任务到达时谁先入队？

答：先把截至片段结束时刻的新到达任务按到达/输入顺序入队，再把当前未完成任务放队尾。规则写进了代码、方法文档和边界单测，避免不同实现口径影响比较。

插图：用 `results/schedule/gantt.png` 替换原理论甘特图，并注“C 调度模拟器实际运行，与理论断言吻合”；用 `results/schedule/comparison.png` 补充指标表。两图不是内核跟踪。

## 第 3 页：nice 多轮控制变量（约 65 秒）

原汇报的 nice 对照只有一轮，而且五个子进程混合了计算和休眠。因此我们另外设计一个固定计算目标，加上可选的同 CPU 竞争者，组合 nice 零和十，形成四个条件。每个条件做十轮，轮内随机顺序，保留种子和所有原始数据。结果是，无额外竞争时，两组经历时间都约零点一八六秒；有竞争时分别约零点三七六和一点八七七秒，而目标 CPU 时间仍在零点一八五秒附近。这说明本次差异主要体现在目标完成期间获得 CPU 的节奏，而不能解释成计算指令变慢。图中点是每轮数据，误差线是样本标准差，不是置信区间。结论只限定在当前机器和负载，也不与原报告的五进程数字混算。

现场命令（短 smoke，仅用于展示流程，不取代正式 10 轮数据）：

```bash
./build/nice_benchmark --rounds 1 --iterations 5000000 --seed 20261029 --output /tmp/nice-live.csv
```

追问：竞争者的总工作量是不是四格都一样？

答：目标的总工作量相同。竞争者固定 nice、CPU、计算代码和每次运算块，持续至目标退出，因此它的总量随目标生命周期变化，原始表记录实际运算量和起止时间。这正是保持目标整个测量窗口持续有竞争的设计；它不是另一个固定工作量的目标任务。

插图：用 `results/nice/nice_comparison.png` 替换方案页右侧待验证区域，或作为下一页实测证据。页脚注明“每条件 n=10；CPU0；固定1亿次；误差线=样本标准差；Ubuntu24.04.3/Linux6.18.55”。轮次图 `results/nice/nice_rounds.png` 可做附录。
